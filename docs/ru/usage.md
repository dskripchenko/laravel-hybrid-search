# Использование

## Конфигурация (`config/hybrid-search.php`)

| Ключ | По умолчанию | |
|---|---|---|
| `connection` | null (по умолчанию) | подключение индекса; направьте его на отдельный PostgreSQL, когда индекс перерастёт базу приложения |
| `table` | `search_documents` | |
| `language` | `simple` | конфигурация текстового поиска для документов, в которых она не указана |
| `queue` | `true` | индексировать в задании после коммита; `false` индексирует сразу |

| `vector.rrf_k` | 60 | k в Reciprocal Rank Fusion |

## Индекс

Одна строка на документ: `type`, `key` (уникальны в паре), `title`, `body`,
`access_key`, `facets` (jsonb), `url`, `language` (regconfig) и генерируемый
`tsv` — заголовок с весом A, тело с весом B. Индексы: GIN по `tsv`, B-tree по
`(access_key, type)`, GIN по `facets`.

## Счётчики

`countsByType()` считает совпадения по типам под фильтром доступа и фасетов,
не глядя на `types()`. `countsBy('status')` считает их по значениям фасета под
всеми фильтрами, кроме фильтра по этому же фасету, — значения сохраняют свои
счётчики, пока одно из них выбрано; документы без фасета не считаются.

## Фильтры и порядок

```php
Search::query('release')->accessKeys($keys)
    ->whereIn('room', [1, 3])          // любое из значений
    ->whereBetween('at', $from, null)  // числовой фасет в границах; null оставляет сторону открытой
    ->whereContains('tags', 'red')     // фасет-список содержит значение
    ->orderByFacet('at')               // числовой фасет вместо релевантности (по убыванию)
    ->get();
```

`orderByNewest()` сортирует по порядку попадания документов в индекс
(первичный ключ, новые первыми): для записей, которые индексируются по мере
появления — сообщений, событий, — это их время, и первая страница находится
обходом индекса сразу. Если хост знает, что совпадений мало (по счётчику с
потолком), `orderByNewest(fewMatches: true)` сортирует совпадения: обход от
новых концов читал бы далеко ради редких или отсутствующих совпадений.

## Большие индексы

Широкое слово может совпасть с сотнями тысяч документов; цену ограничивают:

- `counts(['room', 'author'], upTo: 1000)` — итог и счётчики нескольких
  фасетов за один проход; подсчёт останавливается после `upTo` совпадений.
  `countsByType()` и `countsBy()` тоже принимают `upTo`. Итог, равный
  `upTo`, значит «не меньше».
- `candidates(1000)` — ранжировать только 1000 новейших совпадений.
- `withinNewest(1000000)` — искать только среди новейших документов
  индекса: диапазон первичного ключа, который планировщик сочетает с другими
  индексами, и одна часть таблицы, общая для всех запросов, — она остаётся
  в памяти. Расширьте (уберите), если в нём слишком мало.

Хост может сначала посчитать (с потолком), затем выбрать: мало совпадений —
ранжировать или отсортировать все; много — `candidates()` или обход индекса.
На индексе в 10 млн документов это держит поиск быстрее секунды в 95-м
перцентиле на скромном железе, если PostgreSQL дана память и дешёвое
случайное чтение (`shared_buffers`, `random_page_cost = 1.1` на SSD,
`jit = off`).

## Ранжирование

`ts_rank_cd` запроса websearch учитывается дважды, префиксного запроса —
один раз; точное совпадение ключа добавляет 10. При равенстве выше документ,
проиндексированный позже.

## Векторный поиск

### Хранение

Вторая миграция создаёт `search_chunks`: `document_id` (ссылается на
документы, `on delete cascade`), `ordinal`, `content`, `content_hash`,
`embedding vector(N)`, `model`, `created_at`; HNSW-индекс с
`vector_cosine_ops`. Она выполняется только при включённом `vector.enabled` —
включите его до миграции либо откатите эту миграцию и выполните её снова — и
останавливается с сообщением, если тип `vector` недоступен. Тип никогда не
квалифицируется схемой: установите pgvector в любую схему и добавьте эту схему
в search_path (`ALTER DATABASE … SET search_path = public, extensions`).

### Нарезка на чанки

`Chunking\MarkdownChunker` режет тело документа: ATX-заголовок начинает чанк и
повторяется в начале каждого чанка своего раздела; абзацы упаковываются до
`chunk_chars`; чанк, продолжающий раздел, начинается с последних
`chunk_overlap` символов предшествующего текста; огороженный блок кода
остаётся целым, пока помещается в 1,5 × `chunk_chars`, иначе режется между
строками и заново огораживается; слишком длинный абзац режется между
предложениями, затем между словами. В эмбеддинг идут заголовок, пустая строка
и сам чанк.

### Эмбеддеры

```php
interface Embedder
{
    /** @param list<string> $texts @return list<list<float>> */
    public function embed(array $texts): array;
    public function model(): string;      // хранится с каждым чанком
    public function dimensions(): int;
}
```

`Embedders\OpenAiCompatibleEmbedder` отправляет `{model, input: [...]}` на
`{url}/embeddings` пачками и упорядочивает ответ по `index` — OpenAI,
`/v1` у Ollama, vLLM, LocalAI. Чтобы заменить его, назовите свою реализацию в
`vector.embedder.class` — её создаёт контейнер, так что конструктор может
принимать нужное, — или привяжите её сами:

```php
$this->app->singleton(Embedder::class, MyEmbedder::class);
```

`Embedders\FakeEmbedder` детерминирован (хешированный мешок слов с
необязательной картой синонимов вместо смысла) и запоминает, что он
эмбеддил; `failWith()` заставляет его бросать исключение.

### Индексация

При включённом векторном поиске `Indexer::put()` — а значит, и `IndexRecord`,
трейт `IndexedForSearch` и `search:reindex` — после сохранения документа
перестраивает его чанки. Чанк идентифицируется хешем модели и его
эмбеддируемого текста: неизменённые чанки сохраняют свои эмбеддинги
(копируются внутри базы), в эмбеддер уходят только новые, а документ, в
котором ничего не изменилось, вообще не записывается. Изменение заголовка или
модели заново эмбеддит все чанки. Получение эмбеддингов — медленная операция,
поэтому держите `queue` включённым; сбой эмбеддера роняет задание, и повтор
переделывает документ целиком.

`php artisan hybrid-search:embed` обходит сохранённые документы (`--type=` —
один тип, `--force` — заново эмбеддить и неизменённые чанки, `--chunk=` —
размер страницы): после включения векторного поиска, смены размера чанка или
модели.

### Гибридное ранжирование

`SearchQuery::hybrid()` один раз получает эмбеддинг запроса и берёт первые
`candidates` результатов полнотекстового поиска и первые `candidates`
документов по косинусному расстоянию до их ближайшего чанка, затем сливает два
списка по Reciprocal Rank Fusion: score = Σ w / (`rrf_k` + rank), где `w` — из `vector.weights`. Точное
совпадение ключа добавляет 10, поэтому такой документ по-прежнему первый.
`Hit` сохраняет свою форму: `score` — слитый балл; сниппет — подсвеченный
полнотекстовый фрагмент, а для документа, найденного только по смыслу, —
первые `snippet.max_words` слов его лучшего чанка. `limit()` и смещение
листают внутри слитого списка. `countsByType()` и `countsBy()` остаются
полнотекстовыми. `Hit::$byMeaning` — true у документа, найденного только по
смыслу: его ближайший чанк попал в векторных кандидатов, а ни одно слово не
совпало, — так интерфейс может объяснить, почему он в результатах.

Ближайшие соседи существуют всегда: без `max_distance` гибридный запрос
вернёт и документы, наименее далёкие от вопроса, как бы далеко они ни были.

Если эмбеддер бросает исключение (или возвращает вектор неверного размера),
`get()` выполняет обычный полнотекстовый запрос, `degraded()` возвращает
причину, а исключение передаётся обработчику исключений приложения. При
выключенном векторном поиске `hybrid()` — обычный полнотекстовый поиск, и
`degraded()` сообщает об этом.

## Доступ

У каждого документа один ключ доступа; запрос передаёт ключи того, кто ищет.
Стройте ключи из своей модели прав — для базы знаний это `team:<id>` для
каждой команды, чьи статьи человек может читать. Фильтр — часть условия
WHERE, применяется до ранжирования и ограничения, а не после — и на векторной
стороне тоже: чанки соединяются со своими документами и фильтруются теми же
условиями доступа, типа и фасетов внутри поиска ближайших соседей
(итеративное сканирование pgvector продолжается, пока не наберётся достаточно
подходящих строк). Без `accessKeys()` запрос бросает исключение, пустой список
не возвращает ничего и не вызывает эмбеддер.

## Мультитенантные хосты

В процессе ничего не кешируется. При схеме на тенанта таблицы живут в схеме
каждого тенанта (выполняйте миграции для каждого тенанта; `vendor:publish
--tag=hybrid-search-migrations` копирует их), а задания в очереди несут ваш
контекст тенанта, как и любое другое задание. pgvector устанавливается один
раз на базу в общую схему (например, `extensions`); search_path каждого
тенанта должен её включать (`tenant_42, extensions`) — и во время миграции, и
во время запроса.
